# Frontend route recovery security design

## Scope

Recover two public, read-only page responses without changing authentication,
payments, stored customer data, or the existing website-audit REST endpoint:

- `GET /check-your-website/` on BrandDad Social.
- The Directory public homepage composition lifecycle.

## Data flow and trust boundaries

`Browser -> CDN/host -> WordPress MU loader -> fixed-path renderer -> HTML response`

The Social renderer recognizes only the existing health-check route through the
existing host/path predicate. It emits fixed BrandDad copy, escaped internal
URLs, the existing health-check shortcode, and its already-reviewed inline
assets. The user's website URL continues to cross the separate existing
`POST /wp-json/bds-health/v1/check` boundary; this recovery change does not
alter that endpoint, its validation, quotas, SSRF controls, or storage.

The Directory change adds no endpoint. For the exact public Directory root it
runs before later `template_redirect` callbacks, then asks the already-active
Directory Experience plugin for its existing `render_home()` fragment and
wraps that fragment in the same minimal document shell used by the plugin's
own front-page template. This avoids the later output-buffer collision that is
currently turning a valid template into a zero-byte `200` response. If the
replacement feature or renderer is unavailable, the compatibility layer does
nothing and WordPress continues normally.

## Security decisions

- Public read-only responses require no authentication or authorization.
- No request body, database identifier, file path, or arbitrary template name is
  accepted by the recovery renderer.
- The Directory route gate requires the exact `directory.branddad.social` host,
  exact `/` path, and the replacement plugin's own enabled flag. The exact root
  is authoritative because this installation does not expose `/` through
  WordPress's `is_front_page()` state. Query parameters do not select templates
  or alter rendered markup.
- The existing homepage fragment is generated before `wp_head()` so its own
  registered stylesheet and scripts enter WordPress's output queue in time;
  no asset URL is accepted from the request.
- The captured head replaces only the literal `<body>` token found inside an
  existing JavaScript comment. A legacy full-document optimizer otherwise
  mistakes that comment for the real body boundary and discards the redesign.
- After the exact host/root/feature gate passes, the renderer discards only
  removable output buffers that predate the replacement document. This keeps
  legacy whole-page callbacks from replacing the new document at shutdown.
- At phone and tablet widths the compatibility layer hides the separately
  injected language toggle so the required logo, Search, Account, and Menu
  controls remain inside the viewport. Language links remain available in the
  page footer and content where the existing experience exposes them.
- Directory content remains generated by the existing, namespaced replacement
  renderer; the recovery layer neither duplicates listing queries nor accepts
  request-controlled PHP paths.
- The route decision uses the exact Social host check and fixed health-check
  predicate. It does not dispatch from user-controlled input.
- Dynamic internal links are escaped with `esc_url`; document attributes and
  copy are escaped with the appropriate WordPress helpers.
- The renderer does not call the theme header/footer or start nested output
  buffers, avoiding the collision that produced empty or malformed output.
- No errors, server paths, credentials, or customer data are reflected.
- The existing POST audit endpoint retains its independent rate limiting and
  SSRF protections; no additional network fetch is introduced.

## STRIDE and abuse cases

- **Spoofing / elevation:** no identity or privileged operation exists on these
  GET responses.
- **Tampering:** fixed server-side markup and escaped URLs prevent request data
  from becoming executable HTML.
- **Repudiation:** no state-changing action is performed.
- **Information disclosure:** the response contains only public marketing copy
  and the public audit form.
- **Denial of service:** the recovery renderer performs no outbound fetch; it
  only renders the existing shortcode or existing Directory homepage fragment.
  The expensive scan remains POST-only and quota-controlled.
- **Abuse twin:** an attacker requests the page repeatedly. The response remains
  deterministic and does not trigger a scan or database write.

## Residual risk

The Social page intentionally depends on the existing health shortcode and
REST endpoint. The Directory page intentionally depends on the active
Directory Experience renderer. Future incompatible changes may break either
surface, so focused tests check the route gates and renderer markers, while
live smoke tests check the form root, single H1, non-empty body, and complete
document boundaries.
